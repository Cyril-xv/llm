# 问题重写器四方法：本质、区别与使用时机

> 不用背提示词，记住"本质 + 触发场景"就能灵活运用。

## 一、四个方法一览

| 方法 | 本质 | 解决的问题 | 触发场景 |
|---|---|---|---|
| 分解 Decompose | 复杂 → 拆开 | 问题太笼统，一个 query 搜不准 | 问题里有"和 / 与 / 对比 / 分别"等多个独立知识点 |
| 富化 Enrich | 模糊 → 补全 | 多轮对话丢上下文 | 问题里有"它 / 这个 / 那"等指代词 |
| 多样化 Diversify | 一种说法 → 多种说法 | 用户措辞和文档措辞对不上 | 检索结果太少、topK 全是无关文档 |
| 回退 Step-back | 具体 → 原理 | 细节搜不到，但原理能覆盖 | 提问非常场景化（"我 Redis OOM 了"） |

## 二、逐个拆解

### 1. 分解 Decompose（复杂 → 拆开）

**做什么**：把复合问题拆成若干个相互独立、可单独检索的子查询。

**例子**：
- 原始问题："Mybatis 缓存和 Redis 缓存的区别？"
- 拆成：["Mybatis 一级缓存和二级缓存的原理", "Redis 缓存过期与淘汰策略", ...]
- 每个子问题分别去检索，能命中各自的文档，再合并结果。

**什么时候用**：问题里能明显看到多个独立知识点拼在一起，一个 query 搜出来的都是"四不像"。多跳问题、对比类问题首选用它。

### 2. 富化 Enrich（模糊 → 补全）

**做什么**：结合对话历史，把省略了上下文的指代词补全成一条独立完整的问题。

**例子**：
- 对话历史："Redis 的淘汰策略有哪些？"
- 当前问题："那它的持久化呢？"
- 富化后："Redis 的持久化机制 RDB 和 AOF 是什么？"

**什么时候用**：多轮对话场景。只要用户的提问里有"它 / 这个 / 那个 / 上面说的"这类指代词，检索前必须富化，否则直接拿"它"去搜必然搜不到。

### 3. 多样化 Diversify（一种说法 → 多种说法）

**做什么**：把同一个问题改写成 3 个措辞完全不同但语义相同的变体，分别检索再合并，提高召回率。

**例子**：
- 原始问题："缓存击穿了怎么办？"
- 变体：["热点 key 失效瞬间大量请求打到数据库如何解决", "缓存穿透和击穿的区别是什么", ...]

**什么时候用**：用户说的词和文档里写的词对不上（口语 vs 书面语、黑话 vs 术语）。表现为"搜到了但总觉得漏了关键内容"，topK 数量少。

### 4. 回退 Step-back（具体 → 原理）

**做什么**：先把具体问题"后退一步"抽象成原理级问题，再拿去检索。

**例子**：
- 原始问题："我 Redis 突然 OOM 挂了，怎么排查？"
- 回退："Redis 内存淘汰策略和 maxmemory 配置的原理"
- 文档里未必有"OOM 排查"的原文，但原理章节能覆盖答案。

**什么时候用**：提问过于场景化 / 带有具体环境细节，直接检索大概率空手而归时。

## 三、记忆法：提示词骨架

四个提示词结构完全一样，**只有"任务"一句话不同**：

```
# 角色  你是xxx专家
# 任务  你要做什么       ← 换这一句就是另一个方法
# 输入  {QUESTION} / {CHAT_HISTORY}
# 输出  标准JSON数组 / 纯文本
```

任务四句话就是全部记忆量：

- 分解：拆成相互独立、可单独检索的子查询列表
- 富化：结合对话历史重写为独立完整的问题
- 多样化：生成 3 个措辞不同、语义相同的变体
- 回退：改写为更通用、更本质的原理性问题

## 四、实战决策：什么时候用哪个

```
问题进来 → 直接检索 → 结果准？  → 完事，别用重写器
                     → 结果不准 → 判断属于哪种不准：

   搜到的都是无关文档 / 太散       → 分解
   多轮对话里丢了上下文             → 富化
   检索到了但遗漏关键块 / 结果太少  → 多样化
   文档里没有具体细节               → 回退
```

**核心原则**：

1. **检索结果准就一个都不用**。每次重写都是一次额外 LLM 调用 = 延迟 + 成本。
2. **先看检索结果，再决定方法**，不要默认全流程组合。
3. **组合策略（rewriteQuery）是猛药**：回退 → 分解 → 多样化全上，只有效果差到需要兜底时才用，且只用于离线评估或低延迟容忍场景。
4. **每个方法单独可测**：用调试接口逐个验证输出格式（尤其是 JSON 数组，LLM 偶尔会输出 markdown 反引号导致解析失败）。

## 五、与本节练习的结合

你的 Mybatis.md / Redis.md 两篇文档，测试路径：

1. `/rag/search?query=Mybatis缓存和Redis缓存有什么区别` —— 一个 query 搜，观察结果有多"四不像"
2. `/rewrite/decompose` 拆分后再各搜一次 —— 对比召回是否明显变准
3. 多轮对话：先问"Redis 有哪些淘汰策略"，再问"那持久化呢"—— 直接搜 vs 富化后搜
4. 验证"多样化"对召回量的提升：原始问题搜 3 条 vs 3 个变体各搜 3 条合并
